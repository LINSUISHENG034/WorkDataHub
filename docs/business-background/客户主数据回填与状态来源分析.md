# 客户主数据回填与状态来源分析

> 事实来源：`config/foreign_keys.yml`、`config/data_sources.yml`、`config/customer_status_rules.yml`、`src/work_data_hub/customer_mdm/`、`src/work_data_hub/cli/etl/hooks.py`
> 最后核验：`2026-04-11`
> 适用范围：说明客户回填、主数据维护与状态来源的当前业务含义

## 1. 当前结论

客户主数据与客户状态不是同一个层面的问题，当前代码也按这个原则拆分职责：

- 活动 ETL 域负责把事实数据写入各自主表。
- `foreign_keys.yml` 负责驱动客户等主数据回填到参考表或主数据表。
- Customer MDM 相关 hook 与服务再基于事实表和主数据表生成合同状态与月度快照。

换句话说，回填解决的是“主数据补齐”，状态规则解决的是“经营状态判定”，两者不能混为一谈。

## 2. 当前活动域与客户回填

按当前配置，以下活动域都启用了回填：

- `annuity_performance`
- `annuity_income`
- `annual_award`
- `annual_loss`

这些域在 `config/data_sources.yml` 中启用了 `requires_backfill`，并在 `config/foreign_keys.yml` 中定义了客户相关回填规则。

## 3. 当前客户相关数据分层

从业务角度，可以把当前结构理解为三层。

### 事实层

- `business."规模明细"`
- `business."收入明细"`
- `customer."中标客户明细"`
- `customer."流失客户明细"`

### 主数据 / 参考层

- `customer."客户明细"`
- `mapping."年金计划"`
- `mapping."产品线"`

### 状态 / 快照层

- `customer."客户年金计划"`
- `customer."客户业务月度快照"`
- `customer."客户计划月度快照"`

## 4. 业务状态来源

当前 `customer_status_rules.yml` 已明确不同状态的事实来源：

- `annuity_performance` 来源于 `business."规模明细"`
- `annual_award` 来源于 `customer."中标客户明细"`
- `annual_loss` 来源于 `customer."流失客户明细"`

因此，现状已经不是旧文档中所说的“中标 / 流失尚未接入”或“只影响草案层”的阶段。

## 5. 应如何理解这些状态

- `is_winning_this_year` 反映本年度中标事实。
- `is_loss_reported` 反映本年度流失申报事实。
- `is_churned_this_year` 反映依据当前规则判定出的流失状态。
- `is_new` 是在已有状态基础上推导出的组合状态。

这些字段属于“分析与经营判断”层，不应与客户主数据实体本身混成一张语义含混的表。

## 6. 当前文档应避免的旧表述

以下说法已经不适合继续描述当前现状：

- “`annual_award` / `annual_loss` 尚未配置回填”
- “需要未来再创建 `customer_status_rules.yml`”
- “`customer_plan_contract` 是当前核心落点”
- “中标 / 流失只停留在规划阶段”

这些表述都与当前代码和配置不符。
